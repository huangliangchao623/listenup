# 句子切分算法

这是整个项目里最费劲、也最没有现成答案的一块。

**输入**：一串带时间戳的词

```
[("So", 0.00, 0.18), ("for", 0.18, 0.32), ("the", 0.32, 0.42), ...]
```

**输出**：一串句子，每句有起止时间和文本

```
[{"start": 0.00, "end": 6.42, "text": "So for the last few days, I've been
  thinking about one question that a viewer asked last week..."}]
```

中间这一步的难点是：**"一句话在哪里结束"没有形式化定义。**

---

## 一、为什么纯标点切分不能用

最直觉的做法是按 `. ! ?` 切。写书面语勉强能用，**对口语素材基本报废**。

真实的播客转写长这样（来自项目实际处理的素材）：

```
So for the last few days, I've been thinking about one question that a viewer
asked last week and it's the question how do I stop translating in my head?
Sometimes when you're learning a language like English when you hear something
or read something the first thing you do is you try to Translate it in your
head word for word so that you can understand what you've read or what you've
heard and this just isn't efficient. It takes so much time to translate...
```

问题很明显：

- 一整段可能只有 1–2 个句号
- 说话人会拖长音、停顿、然后接着讲，转写里体现为一个长句
- 按标点切出来是"一大块"，根本没法逐句精听

所以要引入**时间信息**：说话人停顿在哪里。

---

## 二、死路：靠停顿长短判断句尾

第一个想法是"停顿久 = 句子结束"。听起来很合理，实测直接否定。

在一段真实播客里测量：

| 位置 | 停顿时长 |
|---|---|
| `...make English a part of your life.` **后面** | **0.72 秒** |
| `...the English Podcast, Episode 1.` 句**中间** | **0.70 秒** |

**句尾和句中的停顿只差 0.02 秒。**

这就是为什么：

- 阈值设 0.75 秒 → 只抓到部分句尾，大量句子粘在一起
- 阈值设 0.5 秒 → 句中每个逗号都断，切出一堆碎片
- **无论阈值取多少，都会错**

根本原因是人的口语停顿取决于**呼吸和思维节奏**，不取决于语法结构。同一句话，有人一口气讲完，有人中途停两秒想词。

**结论：时间信息单独用不了，必须和标点结合。**

---

## 三、实际算法：五条规则叠加

代码在 `app/listenup/sentences.py`，入口是 `split_words()`。

逐词扫描，对每个位置依次判断：

### 规则 1：句末强标点 → 断

```
.  !  ?  …  。
```

但要先排除缩写（见下文）。

### 规则 2：次标点 + 足够的停顿 → 断成小句

```
,  ;  :  —  、
```

条件是停顿超过 `SENT_PUNCT_GAP`（0.15 秒）。

这一条处理的是"一句话里有很多从句"的情况——口语里非常常见。

### 规则 3：停顿超过阈值，即使没标点 → 也断

阈值是 `SENT_MAX_GAP`（**1.8 秒**）。

这个值**故意设得很大**。因为：

- 我们知道 0.7 秒的停顿时有 50% 是句中
- 但 **1.8 秒的停顿几乎一定是句子结束或换话题**
- 宁可漏断（后面有规则 4 兜底），也不要错断

> 这是这个算法里最关键的一个取舍：**在不确定的地方宁可保守**。
> 因为在听力训练里，"两句合并成一句"只是略长；"一句被切成两半"会让学习者听到半句话。

### 规则 4：单句过长 → 强制切

两个上限：

| 参数 | 值 | 理由 |
|---|---|---|
| `SENT_MAX_DURATION` | 14.0 秒 | 超过这个长度，循环听一遍成本太高 |
| `SENT_MAX_CHARS` | 110 字符 | 屏幕上会排成 4–5 行，读起来累 |

强制切的时候**优先切在次标点处**（逗号、分号），而不是硬切在中间。

被强制切出来的片段会打上 `forced_cut` 标记，供后续处理识别。

### 规则 5：碎片回收

如果一句短于 `SENT_MIN_DURATION`（0.9 秒）或 `SENT_MIN_CHARS`（3 字符），
而且它**看起来没说完**，就并回上一句。

## 四、那些必须处理的边界情况

这几条都是踩坑踩出来的，不处理的话会被用户立刻发现。

### ① 缩写里的句点不是句尾

```python
ABBREVIATIONS = {
    "mr", "mrs", "ms", "dr", "prof", "sr", "jr", "st", "mt", "vs", "etc",
    "e.g", "i.e", "a.m", "p.m", "u.s", "u.k", "no", "fig", "approx", "inc",
    "ltd", "co", "dept", "est", "min", "max", "sec", "hr", "yr", "vol",
}
```

`Dr. Smith` 不能切成 `Dr.` + `Smith`。

还要处理**人名首字母**：

```
J. K. Rowling  →  不能切成 "J." "K." "Rowling"
```

判定方式是：单个大写字母 + 句点 → 不是句尾。

### ② `and` 开头的不能并回上一句

碎片回收规则会把太短的句子并回去。但：

```
He left the room. And then he came back.
```

如果只看"下一句以 `and` 开头就合并"，会把两个独立的句子粘成一句。

**修法**：只有当**上一句没有句末标点**时才允许合并。

```python
# 上一句已经以 . ? ! 结尾 → 说明是完整句子，不合并
if _ends_sentence(prev_text):
    return False
```

### ③ 完整短句不能被误并

```python
def _merge_short(sentences):
    # 只在"未完成的片段"上做合并
    # Sentence.natural_break 标记这句话是自然结束的
    if sent.natural_break:
        return False
```

`natural_break` 是 `Sentence` 上的一个标记，表示"这个断点是标点触发的，不是长度触发的"。
没有它的话，`Yes.` `No.` `Okay.` 这种合法的短句会被反复并回上一句。

### ④ 强制切的碎片要能认出来

规则 4 切出来的片段是**非自然**的，它们更像是"半句话"。
用 `forced_cut` 标记，后续可以：

- 让碎片回头合并
- 或者在界面上给用户提示"这里可能需要手动调整"

## 五、参数总表

全部在 `app/listenup/config.py`：

| 参数 | 默认值 | 作用 | 调大的后果 |
|---|---|---|---|
| `SENT_MAX_GAP` | 1.8 s | 无标点时的断句阈值 | 句子更长、粘更多 |
| `SENT_PUNCT_GAP` | 0.15 s | 次标点后触发断句的最小停顿 | 逗号断得更少 |
| `SENT_MAX_DURATION` | 14.0 s | 单句时长上限 | 单句更长 |
| `SENT_MAX_CHARS` | 110 | 单句字符上限 | 单句更长 |
| `SENT_MIN_DURATION` | 0.9 s | 碎片回收阈值 | 更多短句保留 |
| `SENT_MIN_CHARS` | 3 | 同上（字符） | 同上 |

## 六、怎么给新素材调参

不同素材类型差异很大：新闻播报停顿短，访谈停顿长，课堂录音有大量 "um, uh"。

工具：

```bash
# 在你的素材上扫描参数组合，按"句子长度分布是否合理"自动评分
python tools/tune_split.py

# 对比修改前后的切句质量
python tools/bench_split.py
```

`tune_split.py` 的评分思路：

1. 切出来的句子长度应该集中在 4–10 秒（人一次能跟上的长度）
2. 过短（<2 秒）和过长（>15 秒）都应该扣分
3. 每个句子的文本是否以标点结束，也是信号

## 七、当前效果与局限

**效果**：真实播客素材上，约 **70% 的切分是正确的**（人工抽查）。

**剩下 30% 是什么**：

| 问题 | 占比 | 原因 |
|---|---|---|
| 两句合并成一句 | ~18% | 停顿不够长，且中间没标点 |
| 一句切成两半 | ~8% | 句中停顿超 1.8 秒（想词、换气） |
| 碎片没回收干净 | ~4% | 短句 + 下一句以连词开头 |

**为什么不能更好**：

这条路的理论上限就在这里。要再提升必须引入**语义**信息——

- 用标点恢复模型（如 `deepmultilingualpunctuation`）先给转写补标点
- 或者用一个小语言模型判断"这个位置是否构成完整语义单元"

这两个方向都在 README 的路线图里，但都没实现。

**所以目前留了一个人工出口**：允许用户手动拆分/合并句子。
（这个功能也还没做，`Sentence` 结构里已经预留了 `forced_cut` 标记。）

## 八、为什么不用现成的库

试过 `stable-ts`，它本身也是做这个的。

问题是：**它只有源码包**，安装时需要编译。在本项目的目标环境里（Windows、
受限权限、离线安装）这条路走不通，构建过程直接失败。

于是决定自己写。好处是：

- 完全可控，参数能按素材类型调
- 零额外依赖
- 逻辑透明——出了问题能定位到具体哪条规则

代价是踩了上面所有的坑。

## 九、如果你要改这个算法

改之前先跑测试：

```bash
python -m unittest app/tests/test_sentences.py -v   # 24 个测试
```

这 24 个测试覆盖了：

- 基本标点切分
- 每种缩写
- 人员首字母
- 连词合并的边界
- 强制切与碎片回收
- SRT / VTT 输出格式

**改完一定要跑 `bench_split.py`**，因为单元测试只保证"不破坏已知行为"，
保证不了"整体质量有没有下降"。
